# AWS SNS + SQS

If you're already on AWS and don't want to run a broker, this is your path. SNS fans messages out to SQS queues; shove handles polling, retries, DLQ routing, and consumer supervision. No broker process to provision or maintain — pay AWS for what you use.

## What you need

An AWS account with IAM credentials that have SNS and SQS permissions, and a region selected. For local dev, [LocalStack Pro](https://localstack.cloud/) emulates both services:

```sh
docker run --rm -p 4566:4566 \
  -e LOCALSTACK_AUTH_TOKEN=$LOCALSTACK_AUTH_TOKEN \
  localstack/localstack-pro
```

Set the `endpoint_url` field in `SnsConfig` to `http://localhost:4566` when targeting LocalStack. Omit it entirely for real AWS.

## Install

```sh
cargo add shove --features aws-sns-sqs
```

SQS uses `consumer_supervisor()` — N independent pollers per registered topic. There is no broker-level coordinated-group primitive on SQS, so `consumer_group()` is not available on `Broker\<Sqs\>`. Use `ConsumerOptions::<Sqs>::new()` or `ConsumerOptions::<Sqs>::preset(prefetch_count)` to configure polling behavior.

## Sequenced delivery

Messages for the same group key stay in order. SQS FIFO topics enforce ordering natively: when you declare a sequenced topic, shove provisions FIFO SNS topics and SQS queues and sets the `MessageGroupId` from `T::sequence_key()`; SQS delivers messages in publish order within each group.

FIFO queue names must end in `.fifo` — shove appends this suffix automatically when sequenced topology is declared. The default SQS FIFO throughput quota is 300 messages/second per queue; for higher throughput, contact AWS to raise the quota or switch to a standard (unordered) topic.

See [Sequenced Topics](/guides/sequenced) for the full ordering model, and [Sequenced Pubsub example](/backends/sqs/examples/sequenced) for a runnable walkthrough.

## Consumer supervision + autoscaling

SQS has no broker-level coordinated-group primitive, so `Broker\<Sqs\>` only exposes `consumer_supervisor()` (not `consumer_group()`). The supervisor fans out one polling task per registered topic with a fixed `ConsumerOptions<Sqs>`:

```rust,no_run
use shove::{Broker, ConsumerOptions, Sqs};

let mut supervisor = broker.consumer_supervisor();
supervisor.register::<OrderTopic, _>(
    MyHandler,
    ConsumerOptions::<Sqs>::preset(10),
)?;
let outcome = supervisor.run_until_timeout(signal, drain_timeout).await;
```

`consumer_supervisor()` does not scale poller count on its own — `register` accepts one set of `ConsumerOptions` and runs exactly one consumer per topic.

### Tuning ConsumerOptions

```rust,no_run
use shove::{ConsumerOptions, Sqs};
use std::time::Duration;

let opts = ConsumerOptions::<Sqs>::new()
    .with_prefetch_count(10)
    .with_receive_batch_size(10)                         // SQS max is 10
    .with_handler_timeout(Duration::from_secs(30))
    .with_max_reconnect_attempts(5);
```

- **`with_receive_batch_size(u16)`** — upper bound on messages requested per `ReceiveMessage` call. SQS's hard max is `10`. Default: `0` (= `10`). Each call also requests no more than the handler slots free at that moment (`prefetch_count` minus in-flight handlers), so a received message never waits invisible behind a running handler. With serial handlers that means one `ReceiveMessage` per message, which trades extra requests for fewer duplicate deliveries.
- **`with_handler_timeout(Duration)`** — per-message wall-clock deadline; must be less than the queue's `VisibilityTimeout` so a slow handler doesn't race the broker re-delivering the same message. Default: `30s`.
- **`with_max_reconnect_attempts(u32)`** — cap on SQS client redials before surfacing a `Connection` error. Default: unlimited.

On a standard queue each handler's outcome is settled as soon as that handler completes, in whatever order the messages were received. A finished handler's message is deleted (or retried, rejected or deferred) and its slot reused without waiting for slower handlers received earlier.

`SqsConsumerGroupConfig` exposes the same knobs for the group registry (`with_prefetch_count`, `with_max_retries`, `with_handler_timeout`, `with_concurrent_processing`).

### Autoscaling

For autoscaling within a `min..=max` range driven by `ApproximateNumberOfMessages`, use the backend-specific `SqsConsumerGroupRegistry` directly. It accepts an `SqsConsumerGroupConfig::new(min..=max)` and spawns/retires independent pollers within that range as queue depth changes. The registry also accepts a service-wide handler timeout default via `SqsConsumerGroupRegistry::with_default_handler_timeout(Duration)` — applied to every group that did not set its own. See the [Consumer Groups example](/backends/sqs/examples/consumer-groups) for the full path.

## Batch consumption

`Broker::<Sqs>::batch_consumer()` buffers up to `max_batch_size` messages (or `max_batch_age`, whichever comes first) and hands them to the handler as one call. SQS's `ReceiveMessage`, `DeleteMessageBatch` and `ChangeMessageVisibilityBatch` calls all cap out at 10 entries, so `max_batch_size` above 10 — including this crate's cross-backend default of 500 — is rejected at consumer startup rather than silently clamped down to a 10-message consumer nobody asked for. Set it explicitly:

```rust,no_run
use shove::{BatchConsumerOptions, Sqs};

let options = BatchConsumerOptions::<Sqs>::new().with_max_batch_size(10);
```

Batching on SQS therefore amortises a sink's per-flush cost (one DB transaction, one HTTP request) over **at most 10** messages — a fraction of what other backends' defaults allow.

Whole-batch `Retry`/`Defer` redelivers by resetting every buffered message's visibility timeout to the shared escalating backoff's next delay, rather than deleting and re-sending — topology `hold_queues` do not apply to batch redelivery. `Reject` resets visibility to 0 immediately and relies entirely on the queue's AWS-side redrive policy (`maxReceiveCount`) to move the batch to a DLQ; shove never publishes to a DLQ itself on this backend, so until redrive fires, the handler will keep re-seeing the same rejected batch on the next flush.

While a batch accumulates and while its handler runs, shove keeps the batch's messages hidden (see [Held messages](#held-messages)), so `max_batch_age` and the batch handler's run time are not limited by the queue's `VisibilityTimeout`.

## Held messages

SQS hides a message from other consumers for the queue's `VisibilityTimeout` from the moment it is received. Two consume paths keep received messages locally before their handler runs:

- A sequenced consumer buffers a message whose key is busy, either because a handler is running for the key or because the key waits for a retry to return.
- A batch consumer holds messages from the first one received until the batch flushes, and keeps them while the batch handler runs.

For these messages shove extends the visibility itself. Each consumer reads the queue's `VisibilityTimeout` once when it starts. Every half of that timeout it sets each held message's visibility to the full timeout again, so waiting in a buffer never makes SQS redeliver a message and never raises its `ApproximateReceiveCount`, which a sequenced consumer uses as the retry count. Shutdown releases the buffered messages first, before it waits for any running handler, and the extension stops before it does.

The extension costs two kinds of `ChangeMessageVisibilityBatch` request. The periodic heartbeat sends one request per 10 held messages every half timeout, 4 requests per minute per 10 held messages on a queue with the default 30s timeout. A batch consumer also sends one request at every non-empty flush, before the handler runs, so a workload of frequent small batches adds one request per flush. A consumer that holds nothing sends none. A failed request is logged at `warn`, counted in `shove_backend_errors_total{backend="sns_sqs",kind="consume"}` and retried on the next tick. Each request is bounded to a quarter of the extension period (at most 5 seconds), and a round of requests to half of it, so a slow SQS endpoint cannot stall the consume loop for longer. A request that times out does not stop the requests after it, and a round that runs out of time resumes at the first unsent request on the next tick. Every held message is covered in each round while the requests for all of them fit in half the period: at the default 30s timeout and 50ms per request that is about 1500 held messages per queue consumer. Past that, the tail of a very large buffer can lapse, so bound a sequenced topic's buffer with `max_pending_per_key`. When SQS reports a buffered message's receipt handle as invalid, the message was already redelivered, and a sequenced consumer drops it and the messages queued behind it for the same key and releases them, so they are received again in order under fresh handles.

The extension is best-effort. It runs between the consumer's own SQS calls, so it keeps held messages hidden while those calls return within roughly half the queue's visibility timeout. A consumer whose calls stall for longer than that can still see a held message redelivered, which the at-least-once contract already allows. The same window applies when a buffered message is dispatched: shove does not re-validate its receipt handle first, so between a failed or late extension and the next heartbeat's stale-handle drop, a message that another consumer has since received can also be handled here. On a sequenced topic that is a rare duplicate or overlap for the key, not a loss.

Two limits apply:

- A handler that is running for a single message, on a standard or a sequenced consumer, is not extended. A handler that outlasts the queue's `VisibilityTimeout` is redelivered to another consumer as before, so keep `with_handler_timeout` below it.
- A queue with a `VisibilityTimeout` of 0 hides nothing, so there is nothing to extend, and shove logs a warning at start.

A sequenced or batch consumer fails to start when it cannot read the queue's attributes, which needs `sqs:GetQueueAttributes` on the queue. The IAM list under [Gotchas](#gotchas) already includes it.

## Gotchas

- **Visibility timeout must be greater than handler timeout.** If a single-message handler takes longer than the visibility timeout, the message becomes re-visible on the queue and will be delivered again while the original handler is still running. Set both values consciously. Messages held in a sequenced buffer or an accumulating batch are the exception: see [Held messages](#held-messages).
- **FIFO 300 msg/s default cap.** High-throughput sequenced topics may require quota increases via the AWS console. Standard (non-FIFO) SQS queues have no ordering guarantee and much higher throughput limits.
- **LocalStack endpoint is for local dev only.** The `SnsConfig::endpoint_url` field should be omitted in production; it exists solely to redirect traffic to a local emulator.
- **Region matters.** SQS queues are regional. Cross-region fan-out requires explicit SNS topic ARN configuration — shove does not automatically route across regions.
- **IAM permissions required:** `sns:CreateTopic`, `sns:Subscribe`, `sns:Publish`, `sqs:CreateQueue`, `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:GetQueueAttributes`, and `sqs:SetQueueAttributes` at minimum.
