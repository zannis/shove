# NATS JetStream

If NATS is already in your stack, this backend gives you everything you need: subject-routed messaging with per-key ordering, JetStream-backed durability, coordinated pull consumers, and pending-message autoscaling. Fast, simple, and lighter to operate than AMQP brokers.

## What you need

A NATS server with JetStream enabled. For local dev:

```sh
docker run --rm -p 4222:4222 nats:latest -js
```

The `-js` flag enables JetStream on the server. JetStream streams are provisioned automatically when you call `topology().declare::<T>()`.

## Install

```sh
cargo add shove --features nats
```

## Connect

```rust
// [!include ~/examples/nats/basic.rs:connect]
```

`NatsConfig::new` takes a NATS server URL. Authentication and TLS are populated by writing the matching public fields on the struct after `new` — there are no setter builders, just plain field assignment:

```rust,no_run
use shove::nats::NatsConfig;
use std::path::PathBuf;

let mut config = NatsConfig::new("tls://broker.example.com:4222");
// One of the auth slots — pick whichever the server expects:
config.username = Some("svc-billing".into());
config.password = Some(std::env::var("NATS_PASSWORD")?);
// or token / nkey_seed / creds_file
config.token = Some(std::env::var("NATS_TOKEN")?);
config.nkey_seed = Some(std::env::var("NATS_NKEY_SEED")?);
config.creds_file = Some(PathBuf::from("/etc/nats/user.creds"));
// TLS material:
config.tls_ca_cert = Some(PathBuf::from("/etc/nats/ca.pem"));
config.tls_client_cert = Some(PathBuf::from("/etc/nats/client.pem"));
config.tls_client_key  = Some(PathBuf::from("/etc/nats/client.key"));
```

All slots are `Option<…>` — set only the ones your deployment uses. Static
username/password and token credentials require an encrypted transport — a
`tls://` or `wss://` URL — so reusable secrets are never sent in cleartext. A
local development broker that deliberately uses plaintext must opt in with
`config.allow_plaintext_credentials = true`; that opt-in covers the credential
fields above and nothing else.

Credentials embedded in the URL itself (`tls://user:password@broker:4222`) are
rejected on every scheme, encrypted ones included, and the development opt-in
does not re-admit them. The NATS client never sends URL user-info in the
CONNECT frame, so those credentials authenticate nothing — but it does render
the URL, password and all, into its own connection debug logs. Put the
credentials in `username`/`password`, `token`, or `creds_file` instead. The
`Debug` impl and connection errors redact every credential and the user-info
portion of the URL.

:::warning
Both rules are a behaviour change.

On `tls://` and `wss://`, URL user-info used to be accepted and silently
ignored; it is now rejected. **This includes the case where `username` and
`password` are also set** — that connection authenticated correctly, from the
explicit fields, and it will now be refused until the copy in the URL is
removed. Deleting `user:password@` from the URL is the whole migration; the URL
copy was never what authenticated you. On `nats://` and `ws://` a URL carrying
user-info was already rejected unless `allow_plaintext_credentials` was set,
and that opt-in no longer re-admits it.

`nats+tls://` is likewise rejected up front rather than failing inside the
client; it was never a scheme the client could connect with, so `tls://` is the
substitution.

A `nats://` or `tls://` URL that carries a path, query or fragment
(`nats://broker:4222/?token=…`) is now rejected too. A TCP endpoint is a host
and a port; the client drops everything after the authority on connect, so a
secret placed there authenticates nothing and is only ever logged. This also
catches a missing colon — `nats//broker:4222` parses with the host `nats` and
the real address in the path. `ws://` and `wss://` are unaffected: there the
path and query are part of the address and are sent to the server.
:::

## Declare topology

```rust
// [!include ~/examples/nats/basic.rs:declare]
```

`topology().declare::<T>()` provisions JetStream streams for the topic: the main stream, plus a DLQ stream when `.dlq()` is configured. Sequenced topics declare a single main stream with subject shards (`{queue}.shard.{N}`). Durable consumers are not created here — the consumer runtime creates them on demand when you start consuming. The call is idempotent and safe to invoke on every startup: it reconciles an existing stream to the configured shape (via `create_or_update_stream`) rather than leaving a stale config in place.

## Stream management

By default `declare::<T>()` creates the main stream with shove's defaults — `WorkQueue` retention, file storage, a single replica, and **no size or age limit**. Two NATS-specific `TopologyBuilder` options change how the stream is bounded and who owns it.

### Bounded / replicated managed stream

Use `nats_stream_config` when shove should own the stream but you need it bounded — so a stalled consumer can't grow the file store without limit — or replicated for durability:

```rust,no_run
use shove::{NatsRetention, NatsStreamConfig, TopologyBuilder};
use std::time::Duration;

shove::define_topic!(
    PriceChanges,
    PriceChange,
    TopologyBuilder::new("price-changes")
        .nats_stream_config(NatsStreamConfig {
            retention: NatsRetention::Limits,
            max_age: Some(Duration::from_secs(600)),  // drop messages older than 10m
            max_bytes: Some(1_000_000_000),            // cap the file store at ~1 GiB
            max_messages: None,
            num_replicas: 3,                           // R3 for production durability
        })
        .dlq()
        .build()
);
```

`NatsStreamConfig::default()` is WorkQueue / unbounded / single-replica, so set only the fields you need. On re-declare, **mutable** changes (`max_age`, `max_bytes`, `max_messages`, `num_replicas`) are applied to the existing stream; **immutable** ones (`retention`, storage) make `declare()` fail loudly rather than silently no-op - recreate the stream, or hand ownership to infra with `external()` if you need to change those.

### Bind to an externally-provisioned stream

When infra owns the stream - a Terraform module, a `nats` CLI bootstrap job, or an operator that sets retention, replication, or placement outside the app - use `external()`, the backend-neutral flag Kafka shares:

```rust,no_run
use shove::TopologyBuilder;

shove::define_topic!(
    PriceChanges,
    PriceChange,
    // The queue name must match the externally-provisioned stream name.
    TopologyBuilder::new("CLOB_PRICE_CHANGES")
        .external()
        .dlq()
        .build()
);
```

In this mode `declare::<T>()` does **not** create the main stream — it verifies the stream (named after the queue) already exists and returns an error if it doesn't, so a missing or misnamed stream fails fast at startup instead of silently falling back to a default-configured one. shove still creates and owns its own DLQ stream and the durable consumer on the external stream. Provision the stream before the consumer starts (e.g. order a bootstrap job ahead of the deployment).

On an external stream the consumer never writes into the stream when it settles an outcome.
A `Retry` is the same delayed negative acknowledgement a `Defer` uses: the record stays at its sequence, `hold_queue()` still selects the delay by attempt, and 1 s applies without hold queues.
The retry count comes from JetStream's `num_delivered` instead of the `Shove-Retry-Count` header, so `MessageMetadata::retry_count` is the redelivery count, and a `Defer` or an `ack_wait` expiry consumes the retry budget there.
An exhausted budget dead-letters to shove's own DLQ stream as before, and the dead letter carries that count in `Shove-Retry-Count`.
A shove-owned stream keeps the hold-then-republish path: the incremented copy is published after the delay, and only a `Defer` naks in place.
This is `RetryStrategy::InPlace`, implied by `external()`; [Outcomes](/concepts/outcomes) has the per-backend table.

`external()` and `nats_stream_config()` are mutually exclusive - and both are incompatible with `nats_subjects()` and `sequenced()`, which configure stream *creation* that external mode skips. `build()` panics if they are combined.
`nats_external_stream()` remains for one release as a deprecated alias of `external()`.

## Publish

```rust
// [!include ~/examples/nats/basic.rs:publish]
```

`publisher().await?` returns a `Publisher<Nats>` that publishes to the JetStream stream. Each message is acknowledged by JetStream before `publish` returns.

A header NATS cannot carry is refused with `ShoveError::Validation` before anything is sent. `publish_with_headers` checks every header name (no colon, whitespace, control or non-ASCII character) and every value (no carriage return or line feed), and every publish call checks a sequenced topic's sequence key the same way, since it travels in the `Shove-Sequence-Key` header.

## Consume

```rust
// [!include ~/examples/nats/basic.rs:consume]
```

`consumer_group()` creates a coordinated pull consumer backed by a JetStream durable deliver-group. `NatsConsumerGroupConfig::new(min..=max)` sets the autoscale bounds. The group coordinates via JetStream — only one consumer processes a given message at a time.

### Flow control

Each worker bounds its own in-flight work: a group member, or a consumer started directly or through a supervisor.
It holds `prefetch_count` slots with concurrent processing on and one without, and a prefetch of zero is lowered to one.
Each pull asks JetStream for as many messages as the worker has free slots, so every message it is delivered starts at once.
None waits on the client while its `ack_wait` runs, and a slow handler or a long hold does not get the messages behind it redelivered.
A worker keeps up to two pulls open, each for slots that are free, so a pull for the slots its handlers free is under way while the earlier pull's messages are still arriving or running.
A worker with a single slot, which is every sequential member and any prefetch of one, pulls each message once the one before it is settled, and so pays one pull round trip per message.
Concurrent processing with a larger prefetch restores pipelining.
When the server refuses a pull because the durable's waiting list is full (`Exceeded MaxWaiting`), or ends one on a cluster leader change, the worker probes its connection, and only a failed probe counts as a connection error and spends a reconnect attempt.
Any other status that ends a pull, such as a pull the durable's limits refuse (`Exceeded MaxRequestBatch`, `Exceeded MaxRequestExpires` or `Exceeded MaxRequestMaxBytes`), is a connection error that spends one, so `with_max_reconnect_attempts` ends a consumer whose durable can never take its pulls.
After a refused pull or a leader change, the worker waits before it opens its next pull, and the pulls it already has open go on meanwhile.
The wait is jittered by up to half either way around a base that starts at 100 ms and doubles with each further such pull up to 5 s, so the first wait is 50 to 150 ms and one at the cap is 2.5 to 7.5 s.
Only a delivery resets it.
When the client reconnects, a worker starts any message its open pulls had already delivered, drops those pulls, and pulls again at once, because a server that restarted, failed over or swept the old connection's requests has lost them without a word.

The durable a group or a consumer creates therefore has no ack budget of its own: `max_ack_pending` is `-1` unless `with_max_ack_pending` sets a cap.
Workers attached to one durable, from any number of processes, each keep up to their own prefetch in flight, and a cap is shared by all of them.
A group's registration upserts its durable on every start, so the budget follows the config.
A consumer started directly or through a supervisor creates the durable only when none exists, so a durable an earlier version created keeps the budget it was created with, and the consumer logs a warning naming it.
Lift it in place with `nats consumer edit <stream> <durable> --max-pending=-1` rather than recreating the durable: a recreated durable replays a Limits-retention stream from its start, and deleting the old one drops the messages an Interest-retention stream keeps only for it.

A `Retry` on a shove-owned stream is held un-acked for its delay and gives up its slot for the hold, so the worker goes on with other messages meanwhile.
Holds are bounded on their own, at the same count: a retry that finds every hold taken waits for one and keeps its slot.
A held message, a retry waiting for a hold, and a message whose retry copy or dead letter is being published all get a JetStream progress acknowledgement at least every third of the durable's `ack_wait`, so none of these waits gets the message redelivered.
On a stop or a scale-down, the messages a worker pulled and never started are nak'd without delay, so another consumer takes them at once.
A message held for a retry at that point is left un-acked, and is redelivered once its `ack_wait` expires.

## Sequenced delivery

Messages for the same key stay in order. NATS uses subject-based shard routing: the publisher derives a subject suffix from `T::sequence_key()` and routes to a dedicated shard subject. Each shard consumer is configured with `max_ack_pending: 1`, meaning at most one message per shard is in-flight at a time. Messages for the same key are never processed concurrently.

Keys on different shards are independent. Keys that hash to the same shard share its one in-flight slot, so a message held for a retry delays them as well.

A `Retry` keeps the message at its position on the shard.
The shard holds it un-acked for the attempt's delay, with `hold_queue()` selecting the delay by attempt and 1 s applying without hold queues, then hands it back to the handler in process.
`Defer`, a handler timeout and a handler panic retry the same way.
Through the wait the shard sends a JetStream progress acknowledgement at least every third of the durable's `ack_wait`, so a delay longer than `ack_wait` does not get the message redelivered.
Nothing is republished: the retry count is kept in memory, and an exhausted message is dead-lettered from the original with that count.
Each delivery seeds the count with the message's `Shove-Retry-Count` header plus one for every earlier JetStream delivery, so every hand-off to a new delivery spends a retry.
A stop during a wait hands the message off with a nak, so the next consumer of the shard takes it before anything behind it.
A crash hands it off too: JetStream redelivers the message once its `ack_wait` expires.
So does an `ack_wait` expiry while the progress acknowledgements cannot reach the server.
A message that keeps failing is therefore dead-lettered on delivery `max_retries + 1` at the latest, however often it changes hands.
Until then it holds its shard: every message behind it, other keys included, waits through each hold delay and through the `ack_wait` a crash costs.
A dead letter whose publish fails keeps the message un-acked, and the publish is retried until it lands.
The delay before each attempt doubles from about a second up to a 30 s ceiling and is jittered by up to half either way, so attempts at the ceiling come 15 to 45 s apart.

See [Sequenced Topics](/guides/sequenced) for the full ordering model, and [Sequenced example](/backends/nats/examples/sequenced) for a runnable walkthrough.

## Consumer groups + autoscaling

NATS consumer groups are coordinated via JetStream pull consumers with a deliver group name. Call `broker.consumer_group()` and register topics with a `ConsumerGroupConfig`:

```rust,no_run
use shove::nats::NatsConsumerGroupConfig;
use shove::{Broker, ConsumerGroupConfig, Nats};

let mut group = broker.consumer_group();
group
    .register::<OrderTopic, _>(
        ConsumerGroupConfig::new(NatsConsumerGroupConfig::new(1..=4)),
        || MyHandler,
    )
    .await?;
```

The autoscaler reads the JetStream pending message count and adjusts the number of active pull consumers within the `min..=max` range.

See the [Basic example](/backends/nats/examples/basic) for a complete runnable walkthrough.

## Gotchas

- **Stream provisioning at declaration time.** `topology().declare::<T>()` creates JetStream streams with default storage limits unless you pass [`nats_stream_config`](#bounded--replicated-managed-stream). Ensure stream limits (max bytes, max messages, max message size) match your expected load - streams that hit their limits drop or reject new messages depending on the retention policy. When infra owns the stream, bind to it with [`external`](#bind-to-an-externally-provisioned-stream) instead.
- **De-duplication via `Nats-Msg-Id`.** shove sets the `Nats-Msg-Id` header on every publish (a fresh UUID per call). JetStream de-duplicates within a configurable window (default 120 seconds) — if a publisher retries the same logical message inside that window, JetStream rejects the duplicate. Note that the header is generated per-publish-call, so deduplicating across application-level retries requires the caller to pass a stable id via `publish_with_headers`.
- **Retry copies and dead letters have ids too.** Each copy appends to the id of the delivery it copies: `-r{n}` for a retry copy, where `n` is the retry count the copy carries, and `-dlq` for a dead letter. The second retry copy of a message `abc` is therefore `abc-r1-r2` and its dead letter `abc-r1-r2-dlq`, so `delivery_id` keeps its lineage. A record without an id of its own starts the chain from its delivery, `{stream}.{consumer}.{seq}`, so its first retry copy is `{stream}.{consumer}.{seq}-r1`, and every copy names the delivery it was made from in a `Shove-Copy-Of` header. These ids can be predicted, so a duplicate PubAck for a copy counts only after the consumer has read the stored message back through the stream message-get API (`$JS.API.STREAM.MSG.GET.<stream>`) and found the same copy, by subject, `Shove-Copy-Of` and payload. That costs one stream get per duplicate PubAck, bounded by the client's request timeout. A record redelivered after a crash between publishing its copy and being acked passes the check while its copy is still stored, so the window keeps one copy. Anything else stored under the id fails it, a copy another consumer made of the same record in a shared DLQ included, and so does every duplicate when the consumer's credentials cannot read the stream: the original is redelivered a second later instead of acked, and goes through once the window has passed. That delays the record and never loses it, as long as the durable has no `max_deliver` cap, which holds for every durable shove creates. A copy already consumed from a work-queue stream cannot be read back either, so its record is copied again after the window. A copy keeps the original's headers apart from the JetStream publish directives, matched in any letter case, which applied to the original's own publish: `Nats-Expected-*`, `Nats-Rollup`, `Nats-TTL`, `Nats-Batch-*`, `Nats-Schedule*` and `Nats-Required-Api-Level`.
- **Work-queue semantics by default.** shove provisions JetStream streams with work-queue (delete-on-ack) semantics unless you override `retention` via [`nats_stream_config`](#bounded--replicated-managed-stream) or bind to an infra-owned stream with [`external`](#bind-to-an-externally-provisioned-stream). Work-queue streams allow a single logical consumer over a subject - each `consumer_group()` registration gets its own durable consumer on the stream.
- **JetStream must be enabled on the server.** Connecting to a server without JetStream and calling `topology().declare::<T>()` will return an error. The `-js` flag is required on the NATS server.
- **URL scheme must be one the client can connect with, and must match your TLS options.** The four supported schemes are `nats://`, `tls://`, `ws://`, and `wss://` — the exact set `async-nats` accepts. Anything else, `nats+tls://` included, is rejected before a connection is attempted rather than failing inside the client. Of those, `tls://` and `wss://` are encrypted; `nats://` and `ws://` are cleartext, as is a schemeless address (the client reads it as `nats://`). Setting any of `tls_ca_cert`, `tls_client_cert`, or `tls_client_key` on a cleartext URL is rejected at connect time — use `tls://` or `wss://` to make the encrypted transport explicit, which guards against silent downgrade.
- **Reconnect bounds.** `ConsumerOptions::<Nats>::new().with_max_reconnect_attempts(N)` caps reconnect attempts after a connection drop; default is unlimited. Set this when you want the consumer to surface `Connection` errors after `N` failed redials rather than retry forever.
- **Stream config is tunable; most durable-consumer tuning is not.** Stream retention, storage bounds (`max_age` / `max_bytes` / `max_messages`), and `num_replicas` are configurable via [`nats_stream_config`](#bounded--replicated-managed-stream) (or skipped entirely with [`external`](#bind-to-an-externally-provisioned-stream)); the defaults remain `WorkQueue` / `StorageType::File` / `DiscardPolicy::New` / single-replica / unbounded. The **durable consumers** are declared with `AckPolicy::Explicit` and a 120 s deduplication window. The durable a consumer group or a consumer creates leaves `max_ack_pending` unbounded unless `with_max_ack_pending` sets a cap, since each worker pulls only what it can start (see [Flow control](#flow-control)). The batch consumer's bootstrap durable - created only when nothing pre-declared it - is unbounded too, since a finite budget split across concurrent batch workers pins partially-filled pulls open for the whole `max_batch_age` window (in-flight stays bounded by the pull requests themselves, at most one batch per worker). The remaining knobs are not yet user-configurable, so open an issue if you need them surfaced.
